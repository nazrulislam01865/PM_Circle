# Account, Security, Privacy and Notifications — 2026-11-27

Base: Archive 10.zip. The remaining five settings sections are not redesigned or given new features.

## Implemented changes

- Account: retains the existing validated name/phone update and Edit Profile email workflow. Restores the settings-workspace light/dark/system preview and browser appearance persistence. System changes are observed through the shared hook. Language, time zone and time format now format notification timestamps; time zone also governs quiet hours and digest scheduling. Text size and reduced motion remain scoped to the settings workspace, as labelled. Full application translation and full-site dark-theme coverage are not provided.
- Security: existing password, two-factor and recovery-code screens retained. The new password-validated, throttled other-session revocation action rotates the remember token, uses Laravel's logoutOtherDevices and deletes only the member's other database-backed session rows. The current session is preserved. The member-only Laravel AuthenticateSession wrapper checks password-hash session changes on web requests, including member-accessible public routes. Admin sessions are not changed. Other-device revocation is disabled if SESSION_DRIVER is not database. Already executing requests cannot be retroactively cancelled. Test simultaneous browsers and remember-me behavior before deployment.
- Privacy: settings UI submits only changed field choices. Validated allowlisted patches merge with existing choices; the legacy full-map contract remains compatible. Member-only audiences require active, verified, onboarded community eligibility. The shared profile privacy editor retains the existing My Profile layout; the Account Settings instance uses PMDropdown.
- Notifications: in-app and email are independent, email is opt-in and requires an actually verified email address. Uses the existing notification event key uniqueness. Optional community and challenge alerts continue to work; opt-in course-completion, PMP-result, member-event registration and centralized AI limit rejection notifications now use existing verified triggers. AI limit alerts deduplicate once per reason per UTC day; the actual AI accounting and errors are unchanged. New preference checks on completion/registration use the user already loaded by the request. No per-item read queries or extra calls for disabled topics.
- Instant emails normally queue on the next scheduler tick. Daily digest due at 08:00 local time, weekly Monday 08:00 local time. Changing frequency affects newly recorded activity; turning mail off or choosing Off cancels pending emails. Quiet hours skip optional activity at event time and at delivery time; equal start/end disables the quiet interval. Existing in-app history is preserved. Security and billing notices are not subject to these preferences.
- One additive migration extends notifications with in_app, email_due_at and email_status plus a due-work index. Email-only records are excluded from notification feed, unread counts and read operations. Scheduler discovers at most 200 due recipient/time groups per tick. One uniquely queued job per group claims at most 50 records and uses the existing EmailService. Large digests may be split across messages. Before delivery it checks current opt-in, verified email, topic and quiet hours. Claimed or uncertain sends are not automatically retried (transport could already have accepted them); operations must review `claimed`/`unknown` status rather than replay blindly. Pending mail can be cancelled; already in-flight transport cannot be recalled. Email is not proof of delivery until the configured provider accepts it. No new external packages, tables or separate mail service.

## Explicit outstanding scope

Browser background push requires a push provider/service worker/subscription workflow; career-trend broadcast and news/offers/newsletter campaigns require an actual optional publishing/delivery workflow. These three controls remain unavailable rather than save ineffective preferences. This update supplies completion/registration/limit notifications, not proactive study/event reminders or low-balance threshold forecasting. The legacy direct PMP AI path is not changed. Account language localizes notification date formatting, not the full website. Appearance accessibility remains workspace-scoped where indicated. Do not claim complete implementation of every prototype control.

## Deployment and rollback

1. Back up PostgreSQL and validate on staging. Pause queue/scheduler during the rollout; the new notifier and feed require the new columns. Existing rows default to in_app=true and have no pending email.
2. Install locked dependencies. Clear stale application caches and run the new additive migration. Build frontend and typecheck, then run the Laravel feature tests in the test environment.
3. Verify SESSION_DRIVER=database for other-device revocation; verify password and remembered-session invalidation in two independent browsers, including existing sessions. The app must have its normal scheduler (`php artisan schedule:run` each minute) and default queue worker. Verify `EmailService` with the configured provider and a verified test email. Ensure queue worker timeout permits the delivery job and the connection retry_after exceeds its timeout. Check pending, claimed and unknown statuses for delivery recovery.
4. Resume scheduler/queue and verify in-app-only, email-only, both channels, opt-out, cross-midnight quiet hours and daily/weekly delivery. Test mobile UI and dark preview. Clear/rebuild caches.
5. If rolling back, stop scheduler/queue and revert code before any schema rollback. Avoid dropping delivery columns until email-only rows are reviewed; reverting to legacy feed code without filtering could expose previously email-only notifications to the recipient's in-app feed. Prefer retaining additive columns and deploying a compatible rollback. No production changes performed here.
